# 크레딧 기록 묶기

- 상태: 설계 (2026-11-19).
- 범위: 크레딧 기록(Database > Accounts의 History, 크레딧 버튼 패널)에서 같은 날, 같은 항목의 줄을 한 줄로 묶는다. DB 스키마는 바뀌지 않는다.

## 목적

지금은 기록이 한 건에 한 줄이라, 하루에 Read aloud를 세 번 하면 같은 줄이 세 번 나온다. 서버도 최근 10줄만 보내므로, 반복되는 작은 줄들이 그날 이전의 기록(세션, 지급)을 밀어낸다. 같은 날 같은 항목을 한 줄(횟수와 합계)로 묶어 더 오래된 기록까지 보이게 한다.

## 사용자가 정한 것 (2026-11-19 대화)

1. 날짜별, 항목별로 묶는다. 예: 11월 17일의 Read aloud 세 번은 "Read aloud ×3 −15" 한 줄.
2. 서버가 묶어서 최근 묶음 10개를 보낸다. 브라우저에서 최근 10줄만 묶지 않는다.
3. 날짜는 보는 사람 브라우저의 시간대로 센다.
4. 날짜, 항목, 붙은 내용(세션 제목, 선물 상대, 단어)이 모두 같을 때만 묶는다. 같은 날 세션 두 개는 두 줄이다.
5. 두 곳(Accounts의 History, 크레딧 버튼 패널) 모두 바뀐다.

## 설계자가 정한 것

1. 금액의 부호도 같아야 묶는다. 같은 날 지급 +500과 회수 −100이 "+400" 한 줄이 되면 안 되기 때문이다.
2. 묶음의 시각은 그 묶음에서 가장 최근 줄의 시각이다. 묶음 순서도 이 시각 기준, 최근 것부터다.
3. "×N"은 두 번 이상일 때만 붙고, 항목 이름 바로 뒤, 붙은 내용 앞에 온다. 예: "Practice feedback ×2 · mitigate".
4. 시간대는 쿼리 `tz`(IANA 이름, 예 `Asia/Seoul`)로 보낸다. 없거나 모르는 이름이면 UTC로 센다. 오류를 내지 않는다.
5. 응답 모양은 지금의 `CreditEntry`에 `count`(기본 1)만 더한다. `amount`는 묶음의 합계다.
6. "History · N"의 N은 묶음 수다.

## 목표가 아닌 것

- 묶음을 펼쳐 낱줄 보기.
- 10개보다 더 보기(페이지 넘김).
- 날짜 머리줄로 나눠 보이기. 줄마다 날짜를 그대로 둔다.

## 접근 방법

| 방법 | 장단점 | 결정 |
|---|---|---|
| 서버가 묶고 최근 묶음 10개를 보냄 | 반복 줄이 오래된 기록을 밀어내지 않는다. 시간대를 서버에 알려야 한다 | 채택 |
| 브라우저가 받은 10줄을 묶음 | 서버 변경 없음. 목록이 짧아질 뿐 더 오래된 기록은 안 보인다 | 기각 |

SQLite는 IANA 시간대를 모르므로 SQL `GROUP BY`가 아니라 Python에서 묶는다. 한 계정의 셈에 드는 줄을 모두 읽어 묶는다. 계정 하나의 줄 수는 작다.

## 변경

- `CreditEntry.count: int = 1` (`backend/app/models.py`).
- `CreditRepo.history(user_id, zone, limit=10)`: 셈에 드는 줄(`COUNTS`)을 최근 것부터 읽어 (그 시간대의 날짜, kind, detail, 부호)로 묶는다. `recent`는 낱줄 읽기로 남는다.
- `GET /api/me/credits`와 `GET /api/accounts/{id}/credits`가 `?tz=`를 받아 `history`를 쓴다.
- 프런트: 두 API 호출이 `Intl.DateTimeFormat().resolvedOptions().timeZone`을 `tz`로 보낸다. `CreditLine`이 `×N`을 보인다.
